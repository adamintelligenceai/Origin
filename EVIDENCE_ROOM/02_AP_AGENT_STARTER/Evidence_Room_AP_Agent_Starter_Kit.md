# 2. AP Agent Operating Model (overview)

**What to do.** Treat agents as employees with job descriptions, not as a feature of capture software. Accountability stays human.

**How — the model in one page.**

```
Humans own outcomes.
Agents perform bounded jobs at a published autonomy level.
Evidence is the only promotion currency.
The Orchestrator sequences and stops. It does not become the specialist.
Payment, bank-change, policy exception, and legal dispute never leave the human side of the line.
```

**Autonomy ladder (the only ladder).**

| Level | Name | Agent may | Agent must not |
|---|---|---|---|
| **L0** Observe | Write a shadow file: what it would have done, with evidence | Appear in the live queue as if actionable |
| **L1** Recommend | Put a recommendation + evidence in front of a human | Draft the ERP document or send mail |
| **L2** Prepare | Draft park / match / email held for human release | Commit, send, post, approve, pay |
| **L3** Execute within guardrails | Commit only when **written** gates all pass | Anything outside the gate; any human class |
| **L4** Managed autonomy | Broader execute, sampled, kill-switched | Raise its own ceiling; move cash; write bank data |

Starter Kit permission: **L0 default. L1 when a Measure pack exists. L2 only with Control owner written yes. L3/L4 are Professional-tier decisions.** Buying this kit does not grant L3.

**Unit of promotion.** `agent × legal entity × slice`. Never “the stack.”

**One-increment rule.** A change may raise **one** level **or** add one entity **or** one channel **or** one code family — not two of those together, and never with a model swap in the same change.

**Packet (every hand-off).**  
`case_id`, invoice/statement id, legal entity, vendor_id (or blank), agent_from / agent_to, autonomy_level_applied, decision (`observe`/`recommend`/`prepare`/`execute`/`hold`/`escalate`), confidence + rule, evidence_refs, exceptions[], human_required + reason, next_action (one verb, one owner, one due), cost_envelope.

A chat message is not a hand-off.

**Stack position (first-wave ten).**

```
                 ┌────────── 16 ORCHESTRATOR (queue · gate · stop) ──────────┐
  01 Intake → 02 Validation → 03 Matching → 07 Approval → (human payment)
       │              │              │
      10 Dup     04 Triage ←─────────┘
                     ↓
            05 GR  08 Supplier  09 Internal
```

**Who.**

| Seat | Accountable for |
|---|---|
| Head of AP | Operating model; L0/L1 permission |
| AP Manager | First agent; weekly shadow review |
| Control owner | Human classes; promotion refusal |
| Controller | Any later cash claim (none in this kit’s 90 days by default) |
| Finance Systems | Identity, least privilege, logs |
| Agent | **Never** Accountable |

**What can go wrong.** Shared “AP robot” identity that can park and propose payment. Prompt text used as the only access control. Confidence used as a second signature.

**Control.** Human Accountable named on the job description. Payment-release and vendor-bank write verbs **absent** from the identity sheet. Kill-switch owners: AP Manager and Control owner.

**Measure.** Charters with a human Accountable (must be 1). Identities with payment-release (must be 0). Shadow cases with complete packets / shadow cases.

**Evidence.** This section + signed job description + identity sheet in `Evidence/Starter/Charter/`.

## 01 — Invoice Intake

| | |
|---|---|
| **Owner** | AP Supervisor / Intake Lead |
| **Receives from** | Channels: mailbox, portal, EDI, scan |
| **Hands to** | 02 Validation, 10 Duplicate, 16 |
| **Does not** | Post, match, approve, pay, change vendor master |

**Purpose.** Turn an arriving document into a case the rest of the stack can trust: source stored, hash (or equivalent) recorded, fields extracted, entity proposed, packet handed on. Not a payable decision.

**What to do.** Watch one channel. One case per supplier invoice or credit. Split multi-invoice PDFs. Store the source. Extract header/lines. Mark each field `extracted` / `inferred` / `missing`. Propose legal entity with a rule ID. Park non-invoices. Start the intake clock from the *channel* timestamp.

**How (L0).** Shadow-extract beside the human-indexed invoice. No live queue.

**Who.** Intake Lead Accountable. Processor remains Responsible for the live index.

**Exclusions.** New vendor create; applying printed IBAN; legal mail (route to human hold); employee expenses unless later added as a named slice.

**Human line.** Printed payment details are stored as data, never applied.

**What can go wrong.** Merge of unrelated pages; inferred vendor on a lookalike name; clock started from “now”; PDF footer treated as a bank-change instruction.

**Control.** Source must store or the case dies. Inferred ≠ extracted. Bank text → flag for 10, not a master update.

**Measure.** Intake yield = invoices with required fields complete / invoices received. Field-level extraction accuracy on a labelled sample.

**Evidence.** Source + hash + extract + rule ID for entity.

**First 90-day slice.** One mailbox, existing vendors, PO invoices, one entity.

## 02 — Invoice Validation

| | |
|---|---|
| **Owner** | AP Team Lead |
| **Receives from** | 01 |
| **Hands to** | 03 or 04 or 07 (non-PO), 16 |
| **Does not** | Grant missing-PO exceptions; override tax engine; unblock vendors |

**Purpose.** Prove the invoice is complete, coded-enough, and master-data-fit *before* match. Fail closed.

**What to do.** Check required header, arithmetic (net+tax=gross per your rule), vendor standing, entity allow-list, PO-required policy, tax-engine *compare* (do not “fix” VAT).

**How (L0).** Write pass/fail + codes next to the human validation. Do not block the human.

**Who.** AP Team Lead. Tax owner consulted on EX-TAX-001.

**Human line.** Missing PO on PO-required spend is a policy exception — package it, do not grant it.

**What can go wrong.** Default coding to hit STP. Tax “correction” by the model.

**Control.** Tax engine supremacy. Completeness schema versioned.

**Measure.** Share of validation decisions matching gold on a labelled sample. EX-TAX agent-overrides (target: zero).

**Evidence.** Schema version + engine diff if tax flagged.

## 03 — Matching

| | |
|---|---|
| **Owner** | AP Processor (PO desk) |
| **Receives from** | 02 (match-ready) + 10 clear |
| **Hands to** | 07 / payment-park, or 04 |
| **Does not** | Create GR; widen tolerance; convert 3-way to 2-way |

**Purpose.** Apply the **published** 2-way / 3-way / tolerance table and state the residual. Arithmetic is deterministic. The model may explain; it may not pass a fail.

**What to do.** Compare invoice to PO and, if policy says 3-way, to cumulative GR. Use documented tolerances only.

**How (L0).** Shadow compare log. Human match stands.

**Who.** PO desk owner. Head of AP owns the tolerance table.

**Human line.** Posting outside tolerance, inventing GR, or dropping to 2-way to clear a queue.

**What can go wrong.** Stale GR feed; “find a PO that fits the amount”; UoM ignored.

**Control.** PO must match supplier + entity, not only amount. Stale interface → EX-SYS-001, no guess.

**Measure.** Matching accuracy vs gold using the documented table. Do not target “more matches.”

**Evidence.** Compare log + tolerance version.

**Prerequisite.** Process integrity match rule (diagnostic PI-04) written. If not, map first.

# 4. Exception taxonomy — starter set (27 codes)

**What to do.** Use these codes on every non-straight-through item in the slice. Map ERP reason codes 1:1. Do not run an unofficial parallel list.

**How.** Primary code = what stops posting or payment *now*. Secondary codes are tags. `UNMAPPED` is a holding status with an owner, not a permanent code. Do not invent codes in the queue; raise a change to this list.

**Who.** AP Manager owns the mapping table. Control owner owns versions. Exception owner per row is the default **R**.

**What can go wrong.** “MISC” becomes the operation. Recoding to hide repeats.

**Control.** Misc / UNMAPPED weekly cap review. New codes need a written change.

**Measure.** Mix by code; UNMAPPED count; repeat rate (supplier × code).

**Evidence.** Mapping table version in `Evidence/Starter/`.

This taxonomy is **not** a fraud typology and **not** a legal classification.

| Code | One-line definition | Owner (R) | First action |
|---|---|---|---|
| **EX-PO-001** | PO required by policy; no usable PO on the invoice | Requester / Buyer | Obtain a valid PO **or** documented non-PO path. Do not invent a PO number. |
| **EX-PO-002** | PO present but invalid (unknown, other supplier/entity, cancelled, wrong type) | Buyer | Lookup; correct reference or treat as EX-PO-001. Do not pick a PO by amount. |
| **EX-PO-003** | PO exists but is closed / finally invoiced / blocked | Buyer | Buyer decides reopen (logged) / new PO / reject. AP does not reopen silently. |
| **EX-PO-004** | PO open but remaining qty/value insufficient after **documented** tolerance | Buyer | Change-order / new PO / credit. Do not widen tolerance to fit. |
| **EX-MAT-001** | Price differs from PO/contract beyond documented tolerance | Buyer | Deterministic compare; accept with authority or request credit. Model cannot pass a fail. |
| **EX-MAT-002** | Quantity differs from PO and/or GR beyond documented tolerance | GR owner and/or Buyer | Align GR or credit. Do not receipt to match the invoice. |
| **EX-GR-001** | Receipt required; none against PO/line | Goods-receipt owner | Confirm receipt; GR owner receipts; or reject/credit. Chase on SOP clock. |
| **EX-GR-002** | Receipts exist but are insufficient vs invoice (partial) | Goods-receipt owner | Park for remaining GR or part-process only if policy allows. |
| **EX-DUP-001** | Exact-key duplicate (posted, parked, or paid) | Exception owner | Stop the later item. Do not pay twice. Paid collision → incident. |
| **EX-DUP-002** | Near-duplicate — **indicator, not a finding of wrongdoing** | Exception owner | Human pair review. Confirm distinct or upgrade to EX-DUP-001. No fraud language to the supplier. |
| **EX-MDM-001** | Invoice supplier identity ≠ PO supplier and/or intended vendor master | Master-data steward | Stop. Confirm identity. Do not pick the vendor that matches the amount. |
| **EX-MDM-002** | Bill-to / tax / PO entity is not the entity that should take the invoice | AP Manager (Controller **A** for policy) | Recode or reject for rebill. Do not post to “any group company.” |
| **EX-TAX-001** | Tax amount/rate/code/registration conflicts with engine or policy, or tax block missing | Tax owner | Tax disposes. Agent does not override the engine. Not a tax-compliance certificate. |
| **EX-APR-001** | Required approval not in the official workflow | Named approver | Route/remind on official DoA. Chat “OK” does not count unless policy says how to record it. |
| **EX-APR-002** | Approval exists but fails DoA (limit, dimension, self-approve, expired delegate) | Controller **A**; valid approver **R** | Re-approve under current DoA. Agent cannot raise limits. |
| **EX-COD-001** | Required GL / cost object missing; no documented default | Requester / Buyer | Human codes. Agent may propose from PO or a **versioned** map only. |
| **EX-COD-002** | Cost object present but invalid (closed, wrong entity, not allowed) | Budget owner | Valid replacement. No silent “closest open centre.” |
| **EX-QLT-001** | Source unusable or fails invoice requirements (unreadable, incomplete legal/tax block, hostile/hidden text) | AP Processor; Control if injection suspected | Reject for a usable invoice or quarantine. Do not back-fill identity/bank/tax from history. |
| **EX-QLT-002** | Readable document; extract fails confidence, cite-check, or schema | AP Processor | Human key/correct or re-extract. Do not write to the supplier using uncited amounts. |
| **EX-MDM-003** | Vendor/standing data missing, blocked, or inconsistent — not 001/002 or EX-PAY-001 | Master-data steward | Official MD ticket. AP does not edit master from the invoice. |
| **EX-PAY-001** | Signal that payment destination may change or is inconsistent. **Not a confirmed fraud label.** | Treasury **A**; MD steward + payment preparer | **Hold** (EX-PAY-002). Official bank-change path only. Never take IBAN from the document. |
| **EX-CN-001** | Credit note required and not yet on file / matched | Exception owner | Request CN (human-released mail). No silent net unless policy and ERP support it. |
| **EX-STM-001** | Supplier statement does not reconcile to AP | AP Manager | Work items; request copies; no GL plug. |
| **EX-PAY-002** | Flagged not to pay (policy, bank-change, dispute, missing docs, audit, manual) | Reason owner to clear; payment preparer operates | Stay off proposal until reason clears. Agent cannot lift the hold. |
| **EX-DSP-001** | Business or supplier dispute open — not merely a match fail | Commercial / Buyer / Legal | Hold payment. AP does not settle via goodwill text. |
| **EX-AGE-001** | Item older than buyer threshold and stalled — used **in addition to** the original code | AP Manager (regime); original owner (content) | Re-assign / escalate. Do not close as “no issue” to clear age. |
| **EX-SYS-001** | System/interface/identity/evidence log failed or stale; processing cannot be trusted | Finance Systems; AP Manager for fallback | Fail closed. Do not guess matches on stale GR/PO. |

# 5. Human-vs-agent decision framework

**What to do.** When a case sits on the line, walk the tree. If you are unsure, the case is human. Fail closed. Confidence is not a vote.

**How — the rule.**  
Agents prepare and, when *earned*, execute inside gates. Humans authorise cash, master payment data, policy exceptions, and legal positions.

### Four classes that stay human at every level

| Class | Examples | Agent may | Human must |
|---|---|---|---|
| **Payment release** | Payment run, bank file, positive-pay, cheque, urgent outbound | Review, hold, recommend (Agent 12 is not first-wave execute) | Authorise the run and the file |
| **Vendor bank-change** | IBAN, account, intermediary, factoring payee | Flag EX-PAY-001; collect documents | Dual-control master-data approve — not the invoice processor alone |
| **Policy exception** | Missing PO on PO-required; after-the-fact PO above threshold; related-party; DoA skip | Detect; package | Named policy owner |
| **Legal dispute** | Solicitor letter, statutory demand, formal claim | Stop operational chase; file the packet | Legal / AP Manager |

Related holds treated the same: write-off / credit acceptance above threshold; tax treatment that changes filing position; vendor create/unblock when new, high-risk, or previously blocked; any action after kill-switch.

`human_required=true` is forced by **reason code**. A high confidence score cannot flip it to false.

### Decision tree (first match wins)

```
1. Kill-switch on for stack / agent / vendor / entity / channel?
   → Human (or L0 only). Stop execute.

2. Payment release or bank-file send?
   → Human.

3. Vendor payment-master change, or printed payee ≠ master?
   → Human dual control. Do not update from the invoice.

4. Legal / solicitor / statutory demand?
   → Legal. Stop 08/09.

5. Policy exception (PO-required missing, confirming PO over threshold,
   related-party, DoA skip, off-policy)?
   → Policy owner. Agents package.

6. Write-off, tax-position change, high-risk vendor create/unblock?
   → Human per table.

7. Agent 10 not clear (possible duplicate, anomaly, index down)?
   → No execute on 02/03/payment prep. Human or wait.

8. Packet missing evidence_refs?
   → Reject to sender. No execute.

9. Cost envelope exhausted?
   → Stop. Human or next-day replay.

10. Proposed action inside the published gate for this agent’s level?
    → Only then may a later L3 execute. In this Starter Kit, default = prepare or recommend. Human acts.
```

### By first-wave agent — default line

| Agent | Agent side | Human side |
|---|---|---|
| 01 Intake | Extract, store, propose entity/vendor | New vendor; legal mail; apply printed bank |
| 02 Validation | Completeness, arithmetic, coding **proposal** | Grant missing-PO; clear vendor block; tax-position change |
| 03 Matching | Compare with published tolerances | Post outside tolerance; drop 3-way; create GR |
| 04 Triage | Route, bundle, SLA | Close without resolution; policy close; legal route |
| 05 GR | Find evidence; prepare GR | Post without non-invoice evidence; invent qty |
| 07 Approval | Route, remind, apply published skip | Be the approver; invent delegate |
| 08 Supplier | Template draft; send only if send-gate | Send-gate default; concession; bank; legal reply |
| 09 Internal | Template chase to resolved employees | Chat-as-posting; external domains; off-table escalate |
| 10 Dup/Anomaly | Flag, exact hold | Fraud opinion; vendor block; release paid collision quietly |
| 16 Orchestrator | Assign, stop, surface | Set kill-switch; raise ceilings; specialist work |

### Pressure does not move the line

| Pressure | Still human | Agent help |
|---|---|---|
| Pay today or no shipment | Payment release | Pack + AP Manager |
| “New bank account” on PDF/email | Bank-change dual control | 10 flag; 08 does not reply “we will update” |
| Buyer: “just raise the PO” after the invoice | Confirming PO / policy | Package |
| Warehouse chat: “I received it” | Not a GR | 09 testimony; 05 still needs a document |
| Controller wants close **now** | Period status | Incomplete marked as incomplete |

**ACME — ILLUSTRATIVE.** Steel supplier: “Pay 4500123 to new IBAN or production stops Friday.” Match is clean. Tree: payment is human; new IBAN is bank-change; hold the line this run; official dual control is a *separate* process; next proposal may include the IBAN only after that process. Wrong outcome: recommend release because the match was clean.

**Who.** AP Manager + Controls own the tree. Processors use it live.

**What can go wrong.** “Urgent” as a skip. Model confidence as a second signature. 05 posting GR from the invoice to protect a relationship.
